# RTSP 低延迟与 SR 配对修复验证

## 状态与范围

2026-09-08，继续在 192.168.1.203 的隔离实例验证低延迟方案。以重新读取的站点配置
和生产 FFmpeg argv 为基线，`protocol.modify_stamp=0`。隔离实测没有修改生产配置、
摄像头配置或 Stream Forge 命令生成代码；后续源码集成范围见文末。

本轮已完成同窗根因采集、ZLM 两文件最小修复、ARM64 构建、实际库回归及四台相机
当前格式的组合对照。稳态同源视频发布中位数提前约 30–40 ms，接收端保留音视频
共同 PTS 原点；长头的尾部延迟、大华源 AAC 少量时间步进异常和真实 NVR 呈现仍有边界。
只删除两个 flags 的独立实验没有明显延迟收益，主要收益来自 `rtsp_immediate`。

## 同窗根因证据

前轮约 78–80 ms 的接收端 AV PTS 差属于两个不同冷启动运行，发布抓取在接收阶段前
已经结束。因此该结果不能证明某一级固定把 40 ms 变成 80 ms。

新一轮 `srdiag164-r1` 从发布冷启动起捕获 175 秒，在第 120 秒后同时启动两个原生
ffprobe 双轨接收会话，抓取这些实际 socket 上的 RTP、完整 SR、RTP-Info 和内容哈希。
两路保留站点 flags，唯一媒体变量仍是 `rtsp_immediate` 的关闭/开启。

第二 SR 后 1,207 个匹配的接收 AVPacket，其整数 PTS 与线上 RTP/SR 的原生算法重放
全部相同，残差为 0 tick。7 个同期 2 秒窗口的结果如下，正数表示实验路音频相对视频
更晚；共同会话原点已在差中差中消掉。

| 层级 | 7 个同期窗口的 AV 时间关系差（ms） |
| --- | --- |
| FFmpeg publisher SR/RTP | 46、46、31、31、31、45、45 |
| ZLM relay SR/RTP | 52、52、38、38、38、52、52 |
| FFmpeg 接收 PTS | 52、52、38、38、38、52、52 |

进一步按同内容拆解：ZLM 视频的 SR 映射差比 RTP 媒体坐标差固定少 5 ms，音频固定
多 2 ms，即 NTP 元数据单独增加 7 ms 的 AV 差；AAC RTP 重建的毫秒整数化抵消
0 或 1 ms，得到总增加 6–7 ms。接收器没有再增加偏移。

这是 ZLM 元数据处理边界的实测归因，不是对启动内部每一次 `Stamp::syncTo` 调用的
完整追踪。当前证据不能把旧两轮的 80 ms 精确回算成固定两份 40 ms。

接收侧共同首 NTP 两路相差 40 ms，使视频和音频 PTS 同时平移 40 ms，在 AV 差中严格
抵消。未匹配的 7 个关键帧是 ZLM 补入 VPS/SPS/PPS 共 86 字节，VCL 内容逐个相同；
主分析仍按完整 AU 哈希剔除它们，没有将其计为丢帧或放宽身份门槛。

## 两文件修复

| 文件 | 变更 |
| --- | --- |
| `src/Rtsp/RtspMuxer.cpp` | live 分支对编码器提供的 NTP 使用全轨共同常数平移，移除再次逐轨归零/同步；reset 后重新建立原点 |
| `src/Rtsp/RtspMuxer.h` | 用共同媒体原点和显式初始化标记替代逐轨 `Stamp` 状态 |

原路径会对已经配对的 `ntp_stamp` 再执行 `Stamp::revise/syncTo`，只改 NTP 元数据，
RTP header 保持原值。修复使用：

```text
output_ntp = common_wall_origin + (encoder_ntp - common_media_origin)
```

同一代次所有轨共用该偏移，每个包仍读取编码器当前的 64 位 NTP。0 是有效媒体起点，
正媒体起点下的合法 B 帧 PTS 回退、音频先到及长间隔不再被这一层单独修正。RTP header、序号、内容
和 G711 的精确样本时钟不变，不增加媒体缓存、等待或重采样。

VOD 原分支保留；上游 `modify_stamp=0/1/2` 先产生各自的帧时间戳，本层尊重其结果。
最终候选把 `x-M` 解释为 64 位环上的最短有符号位移，兼容 `FrameStamp` 通过
`uint64_t` 暴露的起始负 PTS 跨零；恰好半环固定取负向。映射接受范围为
`0 <= W + signed_delta(x,M) <= UINT64_MAX`，超出范围明确拒绝，不静默溢出，
也不宣称支持任意 64 位绝对时间排序。普通八小时源偏差在可表示范围内。

该修复不压平 publisher 自身错误 SR 引起的媒体变化，也不重新设计 ZLM 的 RTCP
发送时刻语义。现有发送上下文仍使用最后媒体包的 RTP/NTP 配对；不能将本项局部
配对修复等同于对 UTC 精度和 RTCP RTT 的完整验收。

## 现场对照与运行记录

输出 ZLM 对照使用三个独立实例：公共 source 固定旧 ZLM，仅它连接摄像头；两路
FFmpeg 均启用 immediate，分别发布到旧、新输出 ZLM。各实例逐项读回站点配置，
避免把输入代理变化混入输出修复效果。

`relayab164-r1` 因 2 GB 的 `/tmp` 空间耗尽而无效，日志与结果 JSON 不完整，不参与
验收。测试自有进程均已停止，生产配置、二进制、4 路压缩和 13 个 RTSP 流核验正常。
逐文件核对本地已归档证据的 SHA256 后，删除前轮远端 51 份结果副本，释放约 516 MB。
后续证据改存 `/var/tmp/ipc-rtsp-sr-fix-20260908/results`，每轮开始要求至少 2 GiB 可用。

原生 SR 组合将保持 immediate 和相同输出 ZLM，只比较是否同时移除站点现有的
`-fflags nobuffer` 与 `-rtpflags +rtcp_from_packet`。此前约 2 ms 的成本不能直接从另一
轮的 40 ms 收益里相减；必须直接测新组合的持续发布延迟和接收时间关系。

### 仅输出 ZLM 对照：`relayab164-r2`

重跑完整结束，驱动无失败，两路监听器零抓包丢失。各路按完整 AU 内容对应，将输出
SR 映射到的 NTP 减去编码器的媒体位置，得到本层增加的常数 E：

| 路径 | 视频 E | 音频 E | 额外跨轨差 |
| --- | ---: | ---: | ---: |
| 原 ZLM | 3096 ms | 3134 ms | 38 ms |
| 新 ZLM | 46 ms | 46 ms | 0 ms |

候选视频 369 个、音频 233 个 AU 的 E 共用一个常数，最大差小于 0.000001 ms，
仅含 NTP 小数量化。接收阶段第二 SR 后 1,209 个包的线上模型与原生 ffprobe PTS
逐个一致，残差为 0 tick。共同窗口内 publisher 自身 AV 差为 −3 至 −6 ms，
relay/receiver 差为 −41 至 −44 ms，本层差固定为 −38 ms，接收器新增为 0。
不能将最终 −44 ms 全算作补丁效果，也不能把移除错误元数据偏移称为显示延迟收益。

完整冷启动仍观察到 publisher SR 重锚：原路视频/音频相邻 AU 映射倒退 50/3075 ms，
候选 55/3077 ms。新 ZLM 尊重上游 SR 所产生的变化；这证明局部配对修复有效，
不代表整条链路已经无回退。因此继续同时移除两个 FFmpeg flags 的对照。

SR 的 NTP 与 RTP 应表达同一时刻的时钟对应关系，通常不要求 SR.RTP 等于邻近媒体
包的时间戳。参考 [RFC 3550 §6.4.1](https://www.rfc-editor.org/rfc/rfc3550#section-6.4.1)。

### 同时移除两个 flags：`flagsab164-r1`

两路均使用新输出 ZLM 和 `rtsp_immediate=1`，共用旧输入代理。实验路只移除两个
完整选项对，不改编码器、滤镜、采样率或其他参数。

独立发布延迟分析按原始源 AU 经解码、编码、mux 到实际发布包关联，允许两路输出
PTS 原点不同。两路输入和发布捕获均完整，稳态 2,749 对源帧、22 个完整 5 秒桶：

| 边界：实验减基线 | P50 | P95 | P99 |
| --- | ---: | ---: | ---: |
| 完整 RTP 帧发布观察时刻 | +0.327 ms | +3.954 ms | +6.831 ms |
| 编码包进入 mux | +0.237 ms | +3.915 ms | +5.503 ms |

本轮未发现移除参数产生几十毫秒的固定发布等待，微小中位差仍含观察调度误差。
它不是相对旧 production 组合的直接收益测量，也不是屏幕延迟。

实验路从首 SR 起两轨的 SR/PTS 仿射原点均稳定，没有相邻 AU 映射回退；现场 flags
分支仍有视频 49 ms、音频 3071 ms 启动回退。但默认 SR 的固定相位仍需解释：视频
相对实际发布观察时刻中位超前 928.929 ms，音频 812.459 ms。该计算使用实际最近 SR
及采样时基，没有假设 SR.RTP 等于当前包。不能把固定映射相位直接说成播放延迟。

原始接收验收失败保留：第二 SR 后两路完整输出视频/AAC AU 的 hash 交集均为零，
无法计算同内容跨路接收 PTS 差。各路自身链路完整，1,904 个 RTP 状态重放一致，
1,205 个第二 SR 后接收包与线上 PTS 模型完全相同，均为 0 tick。两 ffprobe 正常退出，
监听器零丢包、无缺失字节。独立 E 判据也通过：现场 flags 分支两轨 E=43 ms，
原生参数分支两轨 E=48 ms。

不同编码启动和分帧可以产生不同码流，零 hash 交集本身不证明媒体损坏。现有输入
捕获在接收阶段之前停止，因此不能补造该阶段的原始源身份；后续需延长输入采集，
从相同源 AU 经各路独立编码结果桥接到接收包。两路 hash 门槛不予放宽，原失败不覆盖。

### 固定共同相位的边界

进一步核对表明，约 0.9 秒相位不是本轮新增的回退或已经测到的缓冲。保留探测包时，
输入 PTS=0 约在 888225.037752 秒到达，输出 ANNOUNCE 约在 888225.886382 秒；
原生输出在写头时取公共 `start_time_realtime`，不是输入 PTS=0 的采集时刻。首 AAC
编码包 PTS=−64 ms 触发外层公共平移，视频和音频从 SR 反推的 mux PTS=0 时刻最终
均为 888225.949779 秒。两轨零点完全相同，约 116 ms 的发包相位差来自不同的产出
时刻，不能解释成两个不同的 SR 原点。

native 路径通过完整 mux→publisher 前缀、各路 publisher→relay→ffprobe 的内容哈希
关联后，367 个视频、232 个 AAC 的 `receiver PTS − 原 mux PTS` 中位数均固定为
−120107 ms；AAC 最大偏差仅 1 tick（0.0625 ms）。全部线上 SR 共同加 0.9 或 1 秒，
1,904 个重放 RTP 状态的 PTS 均不变。该接收路径消去了共同常数，保留音视频相对关系。

旧 `wire164-r1` 原生双参数移除采集重算也已有视频约 +899 ms、音频约 +827 ms 相位。
旧报告的约 +2 ms 是处理/发布延迟差，不是绝对 SR 相位验收。因此不能以非零共同相位
为理由扩大运行时补丁。下一实验继续使用原生 SR，验证 immediate 对相对 PTS 和实际
发布延迟的影响；绝对 producer UTC、跨设备同步和真实 NVR 播放仍需要对应出口验证。

## 原生参数下的 immediate 对照

`native164-r1` 使用候选 ZLM 同时作为共同输入代理和两路输出 relay。两路都移除
`nobuffer` 与 `+rtcp_from_packet`，仅实验路启用 `rtsp_immediate=1`；实际站点配置
仍为 `modify_stamp=0`。输入和发布抓取均延长到 175 秒，第 120 秒开始接收探测。
记录实际采集线程起止，确认覆盖整个接收窗口，原 120 秒稳态分析边界保持不变。

本轮驱动无失败，原生接收匹配通过。10–120 秒稳态 2,750 对同源视频帧的发布观察
差 P50 为 −40.114 ms、P95 为 −27.929 ms，22 个完整 5 秒桶均有有效配对。
两路输入没有重排、丢包或不完整数据，严格逐帧计算的输入首 RTP 到完整发布帧如下：

| 原生参数路径 | P50 | P95 |
| --- | ---: | ---: |
| 默认交织 | 131.690 ms | 138.325 ms |
| immediate | 92.133 ms | 98.475 ms |

接收阶段另有精确桥接的 369 个同源视频 AU：

| 终点：immediate 减原生默认交织 | P50 | P95 | P99 |
| --- | ---: | ---: | ---: |
| FFmpeg 完整 RTP 帧发布观察时刻 | −40.305 ms | −27.991 ms | −4.063 ms |

所有桥接帧的两路 mux PTS 差、接收 PTS 差均为 0。7 个共同 2 秒窗口的接收端

该结果同时证明一帧左右的发布/转发等待被消除、原生接收路径保留相对音视频 PTS。
它不测量屏幕或扬声器，不能据此声称真实 NVR 已降低同样的呈现延迟。

## 四台当前格式的组合对照

四台各采集 175 秒，稳态统计固定为启动后第 10–120 秒，每组有 22 个完整 5 秒桶。

candidate 使用新输出 ZLM、同时删除两个 flags、开启 immediate。同组使用同一 FFmpeg
产物，其余媒体参数和实际站点配置保持一致。此设计隔离共同输入，不能称为完整旧生产
链路与完整新链路的原地替换对照。摄像头配置未改变，本轮没有重跑所有可选编码组合。

### 转发与接收关系

四台接收阶段共桥接 1,138 对同源视频帧。以下使用各自实际接收窗口，不能代替上方
完整稳态风险统计；接收器 `read_intervals` 按媒体 PTS 结束，并非固定 20 秒墙钟。

| 相机 | 同源接收帧数 | 完整 relay 帧观察差 P50 | P95 | P99 |

## 最终负 PTS 边界复核

收尾 review 发现 v1 的无符号大小比较不兼容一类合法内部表示：`FrameStamp` 在
`modify_stamp=1/2` 下可将 DTS=5000、PTS=4960 变为 DTS=0、PTS=−40；其接口再将
−40 转为 `uint64_t`。v1 会把跨零误判为巨大跳变，触发新增的 overflow/underflow
异常。该问题没有出现在本轮四台的实际 `modify_stamp=0` 数据中，但必须避免影响
后续修改配置。

使用改动前 cpp/header 重新编译的旧对象，以及从 v1 实际静态库冻结的对象分别复现：
旧路径 6 组均不抛错，v1 模式 1/2 的 4 组抛错。最终 v2 只把本层差值改为无符号环
上的最短有符号位移，保持共同偏移、输出范围检查、其他 runtime 文件和 RTP header。

| 验证 | 结果 |
| --- | --- |
| 原 14 项 + 新 6 项实际 `FrameStamp` 组合 | 最终库 20 项通过；1.203 原生 ARM64 再运行 20 项通过 |
| G711 / AAC / RTP-NTP 实际库回归 | 最终库全部通过，与上方回归集合一致 |
| 提取最终实际方法的整数边界 | ASan/UBSan 20 项通过，包括跨零、半环选择、输出上下界和 VOD |
| 四台既有捕获坐标的离线 v1/v2 等价 | 94,346 个不同整数值，566,076 次原点/墙钟边界比较，零差异；不作为最终产物实机测试冒名 |

仍有一个**原有边界**：编码器 `RtpInfo::makeRtp` 对负 PTS 使用无符号乘法后再除以
1000，生成的 RTP header 并不是数学上的负采样位置。旧对象和新对象均保留该行为，
测试明确记录，而非把该值当作标准正确结果。本轮只消除新引入的异常，不能宣称
已修复所有“修改时间戳模式 + 负起始视频 PTS”的 RTP/播放器兼容性；需要该输入时应
单独解决编码器的有符号缩放，避免借音频低延迟任务扩大共享包生成代码。
