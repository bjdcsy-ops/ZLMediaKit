# IPC 持续低延迟：参数复核与 RTSP 交织队列修复设计

## 当前决定

验收以持续延迟为准，首包速度不作为采用依据。前轮仅移除两个命令参数的实验没有
证明稳态收益，因此一度暂停；随后定位到 RTSP 交织队列，形成当前受控组合：

| 层级 | 当前方案 | 边界 |
| --- | --- | --- |
| FFmpeg RTSP 输出 | 默认关闭的 `rtsp_immediate`，三个 RTSP 文件新增 51 行 | 只在完成安全初始化后使用既有直通交织器 |
| FFmpeg 命令 | 组合测试同时移除 `nobuffer` 与 `+rtcp_from_packet` | 其余本机参数保持不变，不能只删除 SR flag |
| ZLM live RTSP 输出 | `RtspMuxer.cpp/.h` 使用全轨共同 NTP 平移 | 保留 RTP、样本轴、VOD 分支和上游 `modify_stamp=0/1/2` 语义 |

同窗采集已解释前轮额外 AV PTS 变化。新版 ZLM 不再按轨重复归零 NTP；原生 FFmpeg
SR 保留公共媒体零点，不把变化的发包队列等待写入每轨 SR。原生 SR 的绝对墙钟原点
仍建立于输出写头，但此次逐包模型证明共同常数在单会话接收相对 PTS 中抵消；
不为这个已核实的边界增加通用时钟框架或固定补偿值。

`native164-r1` 在 1.203 上使用新版输入代理和两路新版 relay，实际 `modify_stamp=0`。
两路都使用原生参数，只开关 immediate：2,750 对稳态源帧的发布差 P50 为 −40.114 ms，
严格输入首 RTP 到完整发布 P50 从 131.690 降至 92.133 ms。接收阶段桥接的 369 个源帧
到 ZLM 转发出口仍提前约 40.1 ms，所有帧接收 PTS 相同，7 个音视频共同窗口差均为 0。

候选已构建并完成四台当前格式的隔离组合对照，生产程序和生产参数尚未改变。
后续主分支集成已按该组合调整 Stream Forge 两条命令生成路径，升级时要求先部署
配套 FFmpeg/ZLM。同源帧发布中位数分别提前 39.770、39.388、30.366、39.979 ms；长头全程
P99 差为 +25.772 ms，尾部未统一改善。四路候选接收相对音画中位残差均为 0，视频
最多 1 ms、AAC 最多 1 tick 量化。大华纯代理源仍有少量 3–33 ms AAC 步进，真实 NVR
呈现、音频播放和绝对 UTC 同步仍需对应出口实测。当前代码及完整证据见
[SR 配对与低延迟报告](REPORT-ipc-sr-pairing-low-latency-20260908.md)。
最终兼容性复核另修正了 `FrameStamp` 起始负 PTS 跨零的新异常，仍只修改 NTP 差值。
最终 v2 在 1.203 的双头补测中位数提前 40.178 ms，原始验收通过；20 项实际库测试
及实机回归通过。旧编码器对负 PTS 的 RTP 无符号缩放边界仍保留，不将本轮结果扩称
所有时间戳配置、B 帧及播放器的完整兼容认证。
前轮结果保留在 [RTSP immediate 测试报告](REPORT-ipc-rtsp-immediate-20260908.md)。

## 只移除 SR 参数的稳态复核

两组均在 1.203 同步运行，读同一个隔离相机源，使用此前相同候选二进制，
完整继承本机 `modify_stamp=0` 等配置。两路都保留 `-fflags nobuffer`，
测试路仅删除 `-rtpflags +rtcp_from_packet`。分析器逐项验证了 argv 差异。

每组约 120 秒，排除前 10 秒，以下是同一个源视频访问单元最终发布完整 RTP 帧的观察时间差。
正数表示删除 SR 参数后更晚；统计包含 FFmpeg 输入处理和最终发布，不包含后续 ZLM/NVR/显示。

| 相机 | 同帧数 | 发布差 P50 | P95 | P99 |
|---|---:|---:|---:|---:|
| 海康双头 `.164` | 2,749 | +0.607 ms | +5.739 ms | +10.842 ms |
| 海康长头 `.121` | 2,748 | -0.239 ms | +33.895 ms | +65.046 ms |

小幅发布差不足以判定该组合可采用。进一步复核确认，默认 SR 仍将保留非零 PTS 的媒体
映射到 header 墙钟起点之后，形成持续的未来相位。这再次验证了此前冷启动对照中已发现的
单独恢复默认 SR 的问题，并确认它不只发生在启动阶段。

| 相机 | 删除 SR 参数后：视频映射时刻超前量 P50 | 音频超前量 P50 |
|---|---:|---:|
| 海康双头 `.164` | 3,985.531 ms | 3,970.322 ms |
| 海康长头 `.121` | 1,180.917 ms | 1,120.040 ms |

计算使用每个包之前最近 SR 的 NTP/RTP 配对外推该包的媒体时刻，再与同机包观察时刻相减。
视频全量输出 PTS/序号/NAL 长度、音频逐 AU 的 PTS/长度均校验匹配，没有强行把默认 SR
当成当前包的时间戳。两轨推导出的共同 PTS 零点相同，但它位于 RTSP header 的墙钟附近，
而双头首视频 PTS 已约 3.959 秒。

因此，相邻 SR 增量稳定不能证明 SR 与实际媒体对应正确。SR 的 NTP 与 RTP 字段应描述
同一时刻的时钟关系，且不要求对应相邻的某个实际 RTP 包。
见 [RFC 3550 §6.4.1](https://www.rfc-editor.org/rfc/rfc3550.html#section-6.4.1)。
本测量证明固定相位问题，不证明 NVR 必然增加同等播放延迟；客户端可能重建播放原点。
该组合不满足当前兼容性目标，故没有继续扩测其他相机或落地。

## 已定位的约 41 ms 等待

真实路径是：

```text
ffmpeg_mux.c: muxer <- 日志
  → av_interleaved_write_frame
  → ff_interleave_packet_per_dts / packet_buffer
  → rtsp_write_packet
  → rtp_write_packet / SR 生成
  → TCP 写出
```

当前两轨 RTSP 使用通用 DTS 交织器。`-max_interleave_delta 1` 限制队列内媒体 DTS 的
跨度，单位为微秒；它不是墙钟等待定时器。队列只剩一个包时跨度为零，该包仍等待下次输入。
双头首轮所有已捕获视频包在模型中均由下一次视频 mux 调用释放，因而产生约 40 ms 的等待。
约 40.5 ms 是双头这两轮的队列等待中位数，不是固定定时器，也不是所有相机的每帧等待。
现有参数组首轮的 P95 为 46.663 ms；长头同一模型的中位数约 25.092 ms，P95 为 104.621 ms。

全量音视频 mux 调用的顺序、整数 DTS、采样时基和队列算法重放结果：

| 双头测量 | 队列等待 P50 | 预测出队到 RTP 完整观察 P50 |
|---|---:|---:|
| 首轮，现有参数 | 40.566 ms | 0.438 ms |
| 首轮，同时删两参数 | 40.523 ms | 0.375 ms |
| 反向启动，现有参数 | 40.532 ms | 0.515 ms |
| 反向启动，同时删两参数 | 40.504 ms | 0.494 ms |

首轮 22 个稳态 SR 的发送端内部生成时刻与预测出队触发调用吻合，残差 P50 为 -0.589 ms，
符合 SR 生成函数截断到毫秒及日志观察误差。具体一例：视频 PTS 817110 在日志 3533 行进入队列，
下一视频 PTS 820710 在 3550 行将其释放；预测等待 42.449 ms，内部 SR 生成时刻证明等待 42.116 ms。
该区间位于 SR 生成和 TCP 写入之前，不能用 Nagle 或后续 ZLM 缓存解释。

| 现有参数 | 为什么不能消除本段等待 |
|---|---|
| `max_interleave_delta=1` | 已是最小正整数，但单包队列跨度仍为零 |
| `max_interleave_delta=0` | 关闭最大跨度强制出队条件，可能等得更久 |
| `flush_packets=1` | 在 muxer 写包之后刷新 AVIO，包尚未出交织队列时不起作用 |
| `muxdelay=0` | 已设置；通用 DTS 交织器不读取此值 |
| `max_muxing_queue_size` | 控制 header 前的 ffmpeg 工具队列，不控制本段 libavformat 队列 |

## 最小候选与兼容边界

已实现默认关闭、仅 RTSP 输出生效的 `rtsp_immediate` 布尔选项。
此前的“header 后直接切换”只适合作为当前正 DTS 输入的原型，反证审查后不作为通用实现方案。
推荐启动阶段保留原交织器，满足以下条件后才选择已有的 `ff_interleave_packet_passthrough`：

1. 所有 header 声明的参与交织媒体轨，首包均成功写入对应 RTP 子 muxer。
2. 初始时间戳处理已确定；每轨经外层共同偏移后的首 DTS 非负，子 muxer 未再次独立平移。
3. 用原 callback 显式 flush 已有队列到空，从下一次 callback 开始直通。

任一条件不满足，继续原路径，不额外阻塞现有输出。仅检查 `avoid_negative_ts=KNOWN` 不够：
当前 `max_interleave_delta=1` 可在另一轨到来前就使它固定。也不能中途直接替换 callback，
否则会遗留旧队列；只等待队列自然为空通常也不能触发切换。

这需要 RTSP 内部的小型阶段 callback 和每轨就绪记录，仍可限制在 `rtsp.h`、`rtsp.c`、
`rtspenc.c`；不再声称只加一行 callback 赋值即可通用安全。无需修改 `mux.c`、编码器或 ZLM。
默认关闭时维持原路径，单轨原本已采用 passthrough，其他输出格式不执行此 RTSP 路径。
RTP 包化和 RTSP over TCP 的通道封装保留；包仍由原写包循环写出、释放并处理错误。

实验必须固定现有 `nobuffer`、SR 模式和本机配置，只改变这个开关。
以同源同帧持续发布 P50/P95/P99、同期桶和队列等待为主，启动时间不作为通过依据。
约 40 ms 是本次已定位的候选可削减区间，实际发布/NVR收益必须实测。

开启后跨轨发送顺序会变化，不能预先声称所有 RTSP 用法兼容。尤其需要覆盖 AAC priming、
负 DTS、首个输出轨的不同顺序：`handle_avoid_negative_ts` 会窥探交织队列来选择初始公共偏移，
绕过队列可能改变这一估计。还需检查单轨停供、重连、每轨 RTP 顺序和 NVR 音画同步。
文件回放、突发非实时生产者等场景保持默认路径。这个开关也不代替尚需处理的 SR 映射修复。

具体反例：先写 video DTS=0，随后收到 AAC priming DTS=-1024/16000=-64 ms。
直接直通可能使外层先固定偏移 0，音频 RTP 子 muxer 再独立平移 64 ms；这与共同平移两轨
不同。保守开关遇到子 muxer 独立平移应保留原路径，不宣称会修复原初始化已发生的偏移。

## 验证与证据

测量工具 80 项自测通过，包括交织队列和 SR 相位模型。
原始 TCP 重排计时拒绝仍保留；仅在字节重组完整、零丢包且无其他异常时，独立进行内容身份
与发布时间关联，不使用被拒绝的输入到达时间。

测试结束时生产文件哈希和有效配置未变，四个生产转码进程及原有 13 路 RTSP 流在线，
隔离媒体进程残留为零，本轮 6 份私有配置/认证副本已清理。
证据目录：`.build/field-tests/20260908/steady-latency/`，包含 `SHA256SUMS`、
`sr-phase-audit.json`、两组 `steady-*-independent.json` 和 `mux-queue-replay.json`；不包含相机媒体片段。
