# 移除 FFmpeg 默认参数的实机延迟对照

后续决定：用户要求以持续低延迟验收，启动改善不抵消稳态成本。本报告的测量值保留，
末尾“支持移除”的建议已暂停；生产两个参数保留。单变量复核及约 41 ms 队列的后续设计见
[持续低延迟设计](DESIGN-ipc-sustained-low-latency-20260908.md)。

## 测试范围

2026-09-08，在 `192.168.1.203` RK3588 上，比较现有命令与同时删除
`-fflags nobuffer`、`-rtpflags +rtcp_from_packet` 的命令。
两路使用相同候选二进制、同一个临时相机源、相同转码参数，同时运行。
生产四路转码继续运行；未修改相机编码配置、生产配置或生产二进制。

本报告的主要延迟指标是**同一个源视频帧在两路 FFmpeg 发布 RTP 时的观察时间差**。
它覆盖 FFmpeg 输入等待、解码、编码、复用和发布；不包含之后的 ZLM 处理、
NVR 缓存和屏幕显示，也不代表音频端到端延迟。

| 配置/条件 | 实测设置 |
|---|---|
| ZLM 配置来源 | 1.203 `getServerConfig` 的当前有效值 |
| `protocol.modify_stamp` | `0` |
| `rtsp.directProxy` / `rtsp.lowLatency` | `0` / `1` |
| `protocol.paced_sender_ms` | `0` |
| FFmpeg 输入/输出 | RTSP over TCP |
| 视频编码器 | `hevc_rkmpp`，保持各通道现有滤镜、尺寸和编码参数 |
| 音频 | 保持 `aresample=16000,asetpts=STARTPTS+N/SR/TB` 和 AAC 编码 |
| 探测参数 | 未额外设置 `probesize`、`analyzeduration` 或 `max_delay` |
| 隔离配置 | 仅改监听地址/端口、关闭生产 hook、替换测试 secret 和输出目录 |
| 诊断参数 | 两路对称启用 `debug_ts` 和日志，未单独给移除组增加优化参数 |

## 稳态同帧结果

每组采集约 120 秒，排除最初 10 秒。以下分位数来自每一个成功关联的同源帧，
不是两路各自 P50/P95 的相减。正数表示移除组更晚，负数表示移除组更早。

| 相机 | 当前音频输入 | 同帧数 | 发布时间差 P50 | P95 | P99 |
|---|---|---:|---:|---:|---:|
| 大华圆头 `.108` | AAC 64 kHz | 2,747 | -0.147 ms | +4.691 ms | +33.814 ms |
| 海康圆头 `.120` | AAC 16 kHz | 2,749 | +0.265 ms | +4.685 ms | +31.384 ms |
| 海康长头 `.121` | G711A 8 kHz | 2,748 | -0.070 ms | +36.330 ms | +82.250 ms |
| 海康双头 `.164` | G711U 8 kHz | 2,747 | +2.033 ms | +4.913 ms | +16.339 ms |
| 海康双头 `.164`，反向启动复测 | G711U 8 kHz | 2,744 | +2.036 ms | +6.099 ms | +15.422 ms |

四台的稳态中位差接近零至约 2 ms，没有观察到删除参数后新增固定一帧或几十毫秒的等待。
这不等于每一帧都没有延迟变化：海康长头的尾部差值明显较大，不能据此保证所有相机的
P95/P99 差值小于 10 ms，也不能把长头的短时抖动宣称为已解决。
双头复测把移除组先启动，约 2 ms 的同帧中位差仍出现；这是本次可重复观察到的小幅成本，
不能归结为启动先后顺序，也不能宣称完全零代价。

海康双头完整输入计时的旁证：源视频首个 RTP 包的内核到达时刻，到发布完整帧的观察时刻，
两路 P50 为 **131.558 → 132.410 ms**，P95 为 **138.875 → 139.475 ms**。
两路在复用入口之后的观察等待 P50 为 **41.062 → 41.066 ms**。
现有参数组的 SR 内部生成时刻也支持这段共同等待真实存在，不能只用
`demux → mux` 的约 50 ms 代表整个转码发布延迟。

## 冷启动和缓存

下面来自另一次每组 195 秒的同步对照。计时起点为测试 FFmpeg 创建完成，终点为首次观察到
发布 RTP；是单次冷启动观察值，不是多次启动的分位数，受相机 GOP 相位影响。

| 相机 | 保留参数 | 移除参数 |
|---|---:|---:|
| 大华圆头 `.108` | 2.159 s | 0.928 s |
| 海康圆头 `.120` | 2.180 s | 0.957 s |
| 海康长头 `.121` | 1.151 s | 0.908 s |
| 海康双头 `.164` | 4.141 s | 0.943 s |

移除 `nobuffer` 后，探测数据会被保留并在启动时短暂追赶。双头的输入计时实测中，
首个严格关联的视频帧约在启动 0.927 s 到达复用入口，其输入年龄约 0.901 s；
输入年龄超过 200 ms 的启动帧共 21 帧，最后一帧出现在启动 1.035 s。
大华移除组对应为约 0.889 s、0.859 s、19 帧、0.983 s。
因此，本次观察支持“启动更快、缓存随后消化”，不支持“最初画面完全没有缓存”。

四组 195 秒捕获均覆盖发布端第一份 SR。保留参数时，音频 SR 相邻映射的最大误差分别为
大华 1,169 ms、海康圆头 1,199 ms、长头 375.063 ms、双头 3,145 ms；移除组在本次捕获中均
小于 0.001 ms。这是发布端 SR 映射一致性结果，不是音频播放延迟或端到端音画同步的测量。

## 关联方法和限制

1. 每台相机只建立一个隔离源，两路 FFmpeg 读取同一个源，并保留本机有效配置。
2. 捕获目标绑定到测试 ZLM 监听端口、测试 FFmpeg PID、FD 和 TCP 连接；不采集生产流内容。
3. 用源 RTP 的 SSRC、时间戳、序号及完整 H265 NAL 哈希确定同一个输入访问单元。
   根据每个 RTSP 会话实际 PLAY/RTP/SR 独立重放原始 PTS，不拟合两个会话之间的时间偏移。
4. 将原始 PTS 经日志中的实际时间戳变换关联到解码、编码和复用；重复 PTS、不完整访问单元和
   歧义关联被排除。再用完整启动抓包锚定输出随机 RTP 起点，并逐组验证整个已捕获前缀的
   PTS、序号、marker 和 NAL 长度，关联到实际发布 RTP。
5. 同帧发布差只使用最终输出观察时刻。原始输入计时的拒绝状态保留：长头两路、大华保留组、
   圆头移除组出现 TCP 重排，故不使用这些路径计算绝对输入延迟。它们均为零抓包丢失、
   TCP 字节重组完整；独立的内容身份分析只接受这一项计时限制，其他捕获失败仍拒绝。

输入内核时间戳的校准误差不等于全程测量误差：输出捕获和 FFmpeg 日志仍采用同机用户态
观察时刻，会受到线程调度影响。负的少量 post-mux 观察值保留，没有裁成零。
因此，亚毫秒中位差不应解读为具有亚毫秒精度的确定优化，尾部也包含观察线程延迟。
两路共享 RKMPP/RGA 硬件；首轮四组 CPU 总体忙碌率最大约 19%～23%、最高温低于 34°C，
没有整体 CPU/温度饱和迹象，但不能据此排除局部硬件排队。

同时运行了原生 `stream-compare` 三路画面比较，四组均完成，12 路 VideoToolbox 解码的
时间戳 miss/fallback/ambiguity 均为零。但现场画面静态比例高，排除预热后可同时配对的
2 秒桶覆盖率分别只有 2.9%、2.9%、17.1%、0%，因此未用图像匹配值作为本报告的毫秒结论。

本轮覆盖上述四种当前音频输入下的 H265 视频延迟。没有重新切换每台相机的全部编码模式，
没有测量音频从采样到播放的绝对延迟，也没有测量 NVR 显示延迟。两个参数同时删除，
这组实验不单独量化每个参数的因果贡献。

## 落地范围和证据

正式修改需要调整 Stream Forge 的两个文件：

| 文件 | 现有参数生成位置 |
|---|---|
| `multimedia/compress/infrastructure/services/FFmpegCommandService.java` | 普通命令及命令模板中的 `-fflags nobuffer`，第 102、140 行 |
| `multimedia/compress/infrastructure/builder/FFmpegCommandBuilder.java` | 第 224 行 `+rtcp_from_packet` 及前面的 `-rtpflags` |

本轮只修改隔离测试命令和测量工具，未改这两份业务代码，也未增加 FFmpeg/ZLM 的运行时代码改动。
按后续明确的持续低延迟验收标准，当前结果不作为移除两个默认参数的通过依据：
双头存在约 2 ms 的实测成本，海康长头的尾部延迟问题也未解决。启动和 SR 步进改善另行记录，
不用于抵消这些成本。

最终核验：生产配置、MediaServer、compress 三项 SHA-256 均未变，有效配置差异为空，
`modify_stamp=0`；生产 FFmpeg 进程数为 4，原有 13 路 RTSP 流在线，隔离媒体进程残留为 0。
测量工具的 62 项自测通过；第一次聚合运行因未设置旧抓包工具的模块路径而导入失败，
补齐 `PYTHONPATH` 后通过，没有改动生产代码来使测试通过。

脱敏证据保存在 `.build/field-tests/20260908/ffmpeg-flag-latency/`，包括原始元数据、日志、
分析器及自测、图像比较摘要和 `SHA256SUMS`。相机媒体片段和含认证信息的配置不归档。
主要结果为 `analysis/output-identity-latency-final.json`；原始计时失败记录仍在各组
`results/*/result.json`，未改写为通过。
