# RTSP immediate 交织队列小修与实机验证

## 后续验证

本文记录第一轮保留现场 flags 的实验。后续已定位额外 SR/AV 偏移，完成 ZLM 两文件
修复，并在原生 FFmpeg 参数下测到约 40 ms 发布/转发收益且接收相对 AV PTS 不变。
当前状态见 [SR 配对与低延迟报告](REPORT-ipc-sr-pairing-low-latency-20260908.md)；
下文原始结果及其当时的验收结论保留。

## 状态与范围

2026-09-08，按用户授权实现默认关闭的 `rtsp_immediate`，在 192.168.1.203 RK3588
隔离实例上测试。没有替换生产 FFmpeg、ZLM 或配置，没有修改摄像头配置或 Stream Forge。

当前已证明视频发布端减少等待，同时确认现有 `rtcp_from_packet` 会让视频 SR 映射随之
提前、音频映射基本不动。四台当前音频格式和双头反向启动复测共五组已完成。
经过 ZLM 的 FFmpeg 接收端复测又发现音频相对视频的 PTS 关系变化约 78–80 ms，
因此本补丁未通过播放兼容性验收，保持默认关闭，生产不启用。

## 最小实现

| 文件 | 变更 |
| --- | --- |
| `ffmpeg-rockchip/libavformat/rtsp.c` | 注册输出选项 `rtsp_immediate`，默认 false |
| `ffmpeg-rockchip/libavformat/rtsp.h` | 增加开关、已就绪轨数及每轨就绪标记 |
| `ffmpeg-rockchip/libavformat/rtspenc.c` | 原交织器完成安全初始化、显式排空队列后，切换已有 passthrough |

三个运行时文件共新增 51 行。通用 `mux.c`、RTP 包化、编码器和 ZLM 不增加修改。
启动条件为各轨首包的 RTP 子 muxer 调用及 TCP 写出 helper 成功返回、共同偏移后 DTS 非负、父子时间戳初始化完成且子 muxer
没有独立偏移；不满足时保留原路径。单轨本来已直通，默认关闭及其他容器行为不变。

开关放在输出选项区，例如：

```sh
ffmpeg ... -rtpflags +rtcp_from_packet -f rtsp -rtsp_transport tcp \
  -rtsp_immediate 1 rtsp://127.0.0.1:PORT/relay/STREAM
```

这是实验开关，不是通用的音画同步修复。

## 持续发布延迟

正数表示开启后更晚，负数表示更早。P50/P95/P99 对每个相同源 AU 的最终发布完整帧
观察时间差求分位数，不是相减两路各自分位数。

| 相机 | 当前音频输入 | 同帧数 | P50 差 | P95 差 | P99 差 |
| --- | --- | ---: | ---: | ---: | ---: |
| 海康双头 .164 首轮 | G711U 8 kHz | 2747 | -40.492 ms | -29.681 ms | -2.826 ms |
| 海康长头 .121 首轮 | G711A 8 kHz | 2746 | -31.971 ms | +20.292 ms | +59.240 ms |
| 大华圆头 .108 首轮 | AAC 64 kHz | 2741 | -39.834 ms | -21.264 ms | +5.785 ms |
| 海康圆头 .120 首轮 | AAC 16 kHz | 2749 | -40.790 ms | -21.595 ms | +16.768 ms |
| 海康双头 .164 反向启动 | G711U 8 kHz | 2748 | -40.637 ms | -29.965 ms | -2.859 ms |

双头 11 个完整 10 秒桶的中位差均为 -40.852 至 -40.151 ms，编码包进入复用器（mux 日志）到完整 RTP 发布的中位等待
从 41.097 降至 0.414 ms。长头 11 个桶均为 -34.176 至 -28.254 ms，但尾部仍可能更晚。
源 RTP 到输出的时间进度检查未发现双头有持续增长至几十毫秒的积压。

双头反向启动复测仍有稳定收益，11 个桶的中位差均为 -40.953 至 -40.371 ms。
复用已有严格输入内核计时工具，直接计算被测 FFmpeg 输入连接上该 AU 首个 RTP 到达，
至发布完整 RTP 帧的观察时间，结果如下；没有用此前延迟减去约 40 ms 来估算。

| 双头测量 | 原路径 P50 / P95 / P99 | immediate P50 / P95 / P99 |
| --- | --- | --- |
| 首轮 | 132.508 / 139.082 / 174.112 ms | 92.369 / 99.778 / 133.792 ms |
| 反向启动 | 132.115 / 139.336 / 170.645 ms | 92.100 / 99.455 / 132.476 ms |

两轮输入抓包均完整、零丢失，最大时钟校准区间半宽分别为 0.141、0.507 ms。
发布端观察仍包含线程调度误差，该表不表示摄像头采样到显示或音频播放的绝对延迟。

长头实验路保留原始 `input capture is incomplete` 拒绝：原因是 TCP 重排不满足严格输入
内核计时要求；零抓包丢失、TCP 字节重组完整，故独立内容身份与最终发布时间仍可关联。
该路不用于计算绝对输入到发布延迟，未把原始失败改写为通过。

音频以完整 AAC AU 指纹唯一匹配，双头 1718 对的发布差 P50/P95/P99 为
-0.434/+4.421/+8.129 ms；长头 1718 对为 -0.469/+26.182/+68.892 ms。
视频减少等待不等于音频也减少相同等待。

## SR 与兼容性边界

双头全部 2897 对同源视频和 1860 对相同 AAC、长头全部 2969 对视频和 1862 对 AAC，
输出 PTS 差都为零。会话 PTS 原点和音频初始偏移不能解释以下变化。

按相同内容及各自最近 SR 外推其被映射的媒体时刻：双头视频中位提前 41 ms、长头
视频提前 40 ms，两台音频中位差均为 0。现有 `rtcp_from_packet` 使用实际发送时刻，
所以视频发送更早也改变了它相对音频的 SR 映射。

这是确认的发送端时间关系变化，不能据此声称已发生 NVR 故障，也不能声称 NVR 一定省下
40 ms。下节补充经过 ZLM 后的实际接收端 PTS 测量；真实 NVR 的播放行为尚未验收。
长头已有 SR 映射回退在两路均存在，本次没有证明该开关新增回退类别。

上句仅指剔除前 10 秒后的持续窗口。冷启动的首次 SR 更新另外存在新增或加大的向后
重锚，不能因为开关完成于启动阶段就忽略：

| 相机 | 原路径相邻视频 AU 映射时刻倒退 | immediate 相邻视频 AU 映射时刻倒退 |
| --- | ---: | ---: |
| 双头 .164 | 27 ms | 59 ms |
| 长头 .121 | 146 ms | 183 ms |
| 大华 .108 | 未观察到 | 89 ms |
| 圆头 .120 | 8 ms | 45 ms |
| 双头 .164 反向启动 | 25 ms | 58 ms |

这些是 RTP 到 NTP 映射更新后，相邻 AU 被重建的媒体时刻倒退，不是设备系统时间本身倒退，
也不等于 SR 零点的重锚幅度。例如双头首轮零点调整为原路径 -67 ms、实验路 -99 ms，
叠加正常的 40 ms 视频推进，才得到表中的 27 ms、59 ms 倒退。
大华实验路的 89 ms 事件不存在 SR/RTP 同一观察时刻的排序歧义。
两路原有的音频启动大幅重锚也继续保留，未被本补丁修复。

## 接收端与实际音频解码

使用候选 ffprobe 同时接收隔离 ZLM 转发的两路音视频，不增加时间戳修正或
`nobuffer`。按完整 packet SHA-256、长度、唯一有序内容匹配；两轨均进入第二次 SR
后的共同区间才统计。设同内容包的两路 PTS 差分别为 ΔV、ΔA，在同期 2 秒窗口内计算
`ΔAV = median(ΔA) - median(ΔV)`，去除共同会话原点差，不对两轨分别重新对齐。

| 接收测试 | 共同区间 | 视频 / AAC 对数 | ΔV 中位 | ΔA 中位 | 同期窗口 ΔAV |
| --- | --- | ---: | ---: | ---: | --- |
| `compat164-r2` | 8.333–19.957 s | 291 / 183 | +7 ms | +87 ms | 79.5、80、80、80、80 ms |
| `compat164-r3`，发布进程反序 | 7.316–19.958 s | 317 / 198 | -1 ms | +77 ms | 77、77、78、78、84、86 ms |

结论是音频相对视频的 PTS 关系变化在发布进程反序后仍存在，中位约 78–80 ms，
并非每个窗口固定 80 ms。两轮接收端首轨顺序仍然相同：原路径先 video，实验路先 audio；
本次未单独控制接收首轨因素。约 40 ms 的发布端 SR 差为何在接收端变成约 80 ms，
尚未完成逐段归因，不能直接断言是 ZLM 将其翻倍。

这不是屏幕或扬声器的实测延迟，也不等于已证明实际 NVR 出现可感知音画不同步。
但在维持兼容性的目标下，这个时间关系变化足以阻止默认启用。

实际 AAC 解码另测 15 秒：两路各解码 235 帧、240640 个样本，AAC LC / 16 kHz / mono，
持续 15.04 秒，无解码错误、缺失时间戳或非递增 PTS/DTS。它证明音频数据可解码，
不替代音画同步验收。

采集和分析的原始失败均保留：

- `compat164-r1` 因严格输入计时遇到 TCP 重排，最初的驱动跳过了后置探测，未计作通过。
- `compat164-r2` 首个视频 keypacket 没有 PTS，旧分析器因此报错；原探测结果仍为失败。
  修正分析器后，只审计并排除第二 SR 前的缺失 PTS 包，第二 SR 后缺失仍拒绝。
  另存 `compat164-r2-receiver-reanalysis.json`，没有补造 PTS 或覆盖原始记录。
- `compat164-r3` 使用修正后的分析器，采集完整且无驱动失败。其分析通过表示证据完整，
  不表示测出的音画时间关系满足兼容性要求。

## 回归验证

- 17 项提取真实 C 函数的边界测试通过 ASan/UBSan，包括 callback 错误、队列所有权、
  默认关闭、缺轨、独立偏移回退及显式 drain。
- 13 项真实 libavformat RTSP/TCP 集成测试通过：合成 H264/AAC/G711U，逐包校验随机
  RTP 基值、绝对时间戳、SSRC、每轨顺序、首 SR、共同 header epoch、纯 trailer 排空、
  负 DTS、PTS 重排与非法 DTS 错误处理。
- 构建组件、运行库与 artifact manifest 检查通过，新选项实际帮助输出为默认 false。
- 接收端分析器 14 项、实际解码探测器 8 项回归测试通过。

合成 RTP fixture 不用于解码或音画同步验收。持续延迟表的终点是 FFmpeg 发布 RTP，
包含同机观察线程调度误差；接收端测量另覆盖 ZLM 转发和 FFmpeg 时间戳重建。
两者均未覆盖真实 NVR 的显示、音频播放或其缓冲策略。

测试工具、源码补丁、构建身份与产物，使用 `SHA256SUMS` 核验。未提交或替换生产产物。

下一步先配对 FFmpeg 发布 SR、ZLM 转发 SR 和接收端 PTS，定位新增音画关系变化。
修复应保持共同音视频媒体时钟，使 SR 映射不随交织队列等待变化；不能直接增加固定
40 ms 补偿，也不能直接删除 `rtcp_from_packet`，此前保留非零起始 PTS 的原生 SR
组合仍有秒级未来相位。需要完成该归因及最小修复后，再验收实际 NVR 持续播放延迟。
