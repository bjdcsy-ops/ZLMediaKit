# IPC SR 回退根因与最小修复设计

## 状态与结论

2026-09-08，在 192.168.1.203 的独立候选实例完成双头相机 2×2 参数对照、其余三台相机组合参数验证，以及大华相机输入到代理输出的完整 SR/AAC 元数据采集。本轮只增加诊断工具、证据和设计，没有新增运行时代码修改或替换生产程序。

存在三个互相独立的媒体时钟问题：

1. FFmpeg 探测阶段丢掉启动视频数据，音频等待视频初始化；`rtcp_from_packet` 再把变化的排队时间写入 SR 配对。
2. 大华 AAC 输入 SR 的 NTP/RTP 对应关系有十几毫秒的跳变；现有 AAC 批时间戳修正保留了这些跳变。
3. ZLM `RtspMuxer` 又对 NTP 元数据做一次跨轨同步，但 RTP header 不随之改变，产生新的 SR 配对偏移。

另有独立的相机绝对时间问题：大华 NTP 未启用，显示时间慢约 127 秒，SR 所表达的 UTC 还有近 8 小时的偏差。它不能解释每次 SR 的毫秒级相位变化，须与媒体修复分别处理。

本文保留早期根因与参数实验记录。后续已经完成 RTSP 交织队列小修、ZLM 全轨共同
NTP 平移，以及原生参数下的双头实测：发布等待减少约 40 ms，接收相对音视频 PTS
保持一致。固定共同 SR 墙钟相位不能直接称为新增缓冲，不为其增加通用时钟框架。
当前状态、逐包证据和剩余出口边界见
[SR 配对与低延迟报告](REPORT-ipc-sr-pairing-low-latency-20260908.md) 与
[持续低延迟设计](DESIGN-ipc-sustained-low-latency-20260908.md)。

## 1. FFmpeg 启动与 SR 配对

### 启动链条

`avformat_find_stream_info` 会先读取视频数据。启用 `nobuffer` 时，这些包不进入探测缓存，探测解码器随后关闭；实际 RKMPP 解码器从后面的数据开始。当前长 GOP 相机因此要等待后续可解码视频。

音频已经编码，但 FFmpeg scheduler 在视频编码流未 ready 时将其放入 `pre_mux_queue`。视频首帧到达、所有输出流 ready、RTSP header 写出后，这些 AAC 包集中发送。该等待发生在常规 mux interleave 之前，减小 `max_interleave_delta` 不能解除它。

单变量实测证明保留探测包恢复了启动段可解码视频；当前没有输入 NAL 类型或解码帧内容记录，不能声称已精确识别被消耗的首个 IRAP。

### 双头相机 2×2 对照

| FFmpeg 输入/输出参数 | 首视频 demux→decode | 首 AAC 编码后→mux | relay 音频最小间隔 | 结果 |
|---|---:|---:|---:|---|
| 原命令 | 3195 ms | 3124 ms | −3055 ms | 启动积压与 SR 配对回退 |
| 只移除 `-fflags nobuffer` | 24 ms | 82 ms | −752 ms | 启动改善，探测缓存追赶仍使 packet-SR 跳变 |
| 只改为 `-rtpflags 0` | 3201 ms | 3162 ms | −3894 ms | 15 次 NtpStamp 3 秒异常处理，不能单独采用 |
| 同时调整两项 | 18 ms | 73 ms | 64 ms | 本轮 615 个 AAC 单元，614 个间隔全部 64 ms |

`rtcp_from_packet` 将当前包的媒体 RTP 坐标与发送当下的 NTP 配对。初始旧包积压随后清空，等于改变这两个坐标的对应关系；SR.NTP 本身始终向前，也会造成接收端媒体时间回退。

原版 SR 模式使用公共起点和墙钟推算 RTP。单独恢复该模式时，双头首视频媒体 PTS 已约 3.96 秒，而 SR 从输出 header 时刻附近起算，差值超过 ZLM 的 3 秒阈值。逐包模型包含这个异常分支，重现实际日志和全部捕获范围内的 publisher→relay 唯一内容时间戳，残差为 0 tick。

### 四台相机组合参数验证

| 相机 | 首 RTP 耗时：原命令→组合参数 | 组合后首 AAC 编码排队 | relay AAC 间隔 | relay 自发视频 SR 首段相位变化 |
|---|---:|---:|---|---:|
| 大华 108 | 2.066→0.908 s | 48 ms | 612 个，全部 64 ms | +639 ms |
| 海康 120 | 2.177→0.936 s | 33 ms | 614 个，全部 64 ms | +544 ms |
| 海康 121 | 0.976→0.761 s | 64 ms | 611 个，全部 64 ms | +583 ms |
| 海康 164 | 4.129→0.933 s | 73 ms | 614 个，全部 64 ms | +415 ms |

首 RTP 耗时按启动日志/采集锚点计算，不是摄像头采样到 NVR 显示的绝对延迟。108/120/121 的原命令来自前一轮固定候选产物冷启动；164 来自本轮对照。因此前三行不能当作同一时刻的端到端延迟 A/B。

30–35 秒窗口内，视频 demux→mux P50 约 45–50 ms，AAC 编码后→mux P50 约 0.11 ms；没有发现持续增加的积压。121 仍有尾延迟：本轮视频 P95 142 ms、最大 417 ms，旧基线 P95 90 ms、最大 327 ms。需要成对长测，不能据此断定组合参数引入或消除了尾延迟。

## 2. 大华 AAC 输入 SR

输入捕获 3236 个完整 AAC 单元，其中代理读者覆盖的 2506 个单元与输入逐个长度/哈希相同，没有缺失或重排。原始成批共用 RTP 时间戳仍存在，但现有样本轴修正已经处理它。

代理 8 个异常间隔为 `32、0、32、2、22、30、22、18 ms`，全部位于一份新相机 audio SR 之后。相邻 SR 的配对相位变化为 `+16、−16、+15、−15、+6、+13、+6、+1 ms`。

计算方式：

```text
SR 相位变化 = NTP 增量 − RTP 增量 / 采样率
代理 AAC 间隔 ≈ 16 ms + SR 相位变化
```

依据实际 RTCP NTP 截断、NtpStamp 浮点增量和 AAC 相位修正代码逐事件回放，**2506 个代理 RTP 时间戳与实测绝对值全部相同，2505 个间隔全部相同**。近似公式中剩余的 1 ms 也已由数值转换和重新锚定解释，未留作未知网络抖动。

相机这 11 份 audio SR 的 NTP/RTP 均向前走；初始间隔分别为 4256/4240 ms，后续 NTP 约 4973–5025 ms，RTP 约 4960–5040 ms。这证明问题在其配对关系，不能仅据此断言相机发生系统时间回拨。

## 3. ZLM 生成 SR 时的重复同步

现有路径：

```text
encoder 设置 RTP header 和 64 位 ntp_stamp
  → RtspMuxer::onRtp 对 ntp_stamp 调 Stamp::revise
  → Stamp::syncTo 再次调整跨轨相对时钟
  → 仅覆盖 ntp_stamp，RTP header 保持原值
  → RtcpContextForSend 把这两个值写入 SR
```

组合参数下 publisher SR 相位稳定，relay 媒体 RTP 也连续，但 relay 自发视频 SR 的首段仍跳 415–639 ms。

使用未修改的 `src/Common/Stamp.cpp` 做最小本地复现：音频相对时钟为 575 ms，视频为 160 ms；音频同步时发现二者差 415 ms，大于 300 ms。音频不允许回退，于是反向将视频 master 的内部相对时钟从 160 推到 575；下一视频原应得到 200，却得到 615。RTP header 没变，NTP 元数据单独多出 415 ms，与双头抓取一致。

该同步逻辑与本轮参考的上游相同，之前的小修没有新增它。`modify_stamp=0` 也不会绕过这条 `RtspMuxer` 内部路径。

|---|---|
| 1.203 `timedatectl` | `Asia/Shanghai`、`NTP=yes`、`NTPSynchronized=yes` |
| 1.203 与诊断主机 epoch 对照 | 差值约 0.31 秒，半 RTT 不确定度约 0.28 秒，远小于相机偏差 |
| 大华当前时间 API | 显示 `2026-09-08 17:51:54`，诊断主机当时约 `17:54:01` |

相机时间应单独同步到已验证可用的时间服务器，再检查显示时间与 SR UTC。此项本轮只读，没有修改。固定时间偏差与每几秒的 SR 相位跳变分别验收，不在 ZLM 中硬编码时区补偿。

## 推荐实现顺序与范围

### A. 参数调整暂停，保留现有低延迟基线

此前候选为同时移除输入的 `nobuffer` 与输出的 `+rtcp_from_packet`。后续实测发现双头有可重复的
约 2 ms 稳态发布成本；单独移除 SR flag 的持续相位问题也已复核。因此暂不执行两项参数调整，
也不修改用户可能增加的其他 RTP flags。后续优先单变量验证 RTSP 交织等待的削减。

当前本机命令来源已定位到 Stream Forge：

- `FFmpegCommandService.generateCommand()` 与 `generateCommandTemplate()` 都添加 `nobuffer`，两条路径同时处理。
- `FFmpegCommandBuilder` 统一添加 `+rtcp_from_packet`。

已存在的 opt-in `rtcp_from_packet` 选项及当前命令保留。不要替换为上游 ZLM 配置文件；
站点 `modify_stamp=0` 和其他有效设置仍是主要验收前提，未来配置值照常生效。

### B. 修复 RtspMuxer 的 NTP 元数据映射

仅修改 `src/Rtsp/RtspMuxer.cpp/.h` 的 live 分支，取消对已经形成的 RTP/NTP 配对执行第二次 `Stamp::revise/syncTo`。整个 mux 代次建立一组公共原点：

```text
out.ntp_stamp = shared_wall_origin + (in.ntp_stamp − shared_media_origin)
```

行为约束：

- 所有轨使用同一个常数偏移，保留实际音画偏移；不能各轨独立用首包发送时间设零。
- 每包仍读取 encoder 产生的 64 位 `ntp_stamp`，没有冻结第一份输入 SR，也不从 32 位 RTP 重新推导 UTC。
- 保留 RTP header、序号、内容、G711 的精确样本 RTP 与 NTP 配对。使用有符号差并检查边界，0 是有效起点。
- `resetTracks` 清除公共原点，在新代次首包同时重建媒体原点和墙钟原点，避免复用旧墙钟起点；普通停供和合法 B 帧 PTS 反序不触发重锚。
- VOD 原分支保留；上层 `modify_stamp` 的既有语义先执行，再按同一规则转换其输出，不能写死仅适用于配置 0。

这一项修复的是 SR 配对相位和跨轨一致性。上游 `RtcpContextForSend` 仍使用最后媒体包的 NTP 元数据作为 SR.NTP；本方案没有把它包装为“严格报告发送 UTC”完整修复。若后续确实要求采样 UTC 保真或严格 SR 发送时刻，需另行设计当前时刻投影及输入参考钟传递。

### C. AAC 仅对已确认的直播批输入跟随小幅 SR 校正

只在当前严格匹配的 AAC-hbr、基本两字节 AAC-LC ASC、1024 samples/AU、单/双声道、无显式 VOD，并已观察到跨包完整 AU 共用时间戳时启用。沿用现有 raw RTP 批相位上限与序号/SSRC/分片边界。

在 `ext-codec/AACRtp.cpp/.h` 内复用 G711 已验证的思路：样本数给出连续主轴，先去掉 raw RTP 批相位，再观察 SR 带来的校正；正常小幅校正逐步跟随，不让一份 SR 直接把一个 16 ms AU 改成 0 或 32 ms。建议先以现有 G711 的 1 ms 观测死区、每秒最多 1 ms 校正作为验证起点，保留微秒或有理数余量，避免每 AU 截断累计误差。

以此速率消化 16 ms 的固定校正大约需要 15–16 秒。这是时间轴的收敛时间，并非增加 15 秒媒体缓存；仍需验证收敛期音画偏移是否符合现场要求。

兼容性约束：

- 不增加媒体缓存、等待定时器或重采样，不丢补 AAC 单元；校正的是时间标签，不是额外播放缓冲。
- 包丢失、SSRC/序号重启、格式变化、分片损坏、真实大幅时间变化继续作为明确边界，不能无限压平。
- 持续大校时需明确重锚和日志策略；可按 G711 的 `250 ms / 2 秒` 规则做起始方案，但相机近 8 小时偏差先修配置，不能当作普通 slew 追赶。
- HE-AAC、960 samples、未知/复杂 ASC、未出现批证据的常规 AAC、显式识别的 VOD 不进入新增校正路径。未声明回放或仅给出 `npt=0-` 的输入无法仅凭现有 SDP 可靠识别，保留这一限制并覆盖测试。
- 保持 G711 本轮实现不再扩张；不改全局 NtpStamp、Frame API 或建立通用音频时钟层。

## 验收与已知边界

实施每一步后先跑针对性回放，再在 1.203 做隔离实机测试，保持步骤可单独比较。

| 验收项 | 必须核对的结果 |
|---|---|
| 大华源数据精确回放 | AU 长度/哈希全部守恒；修复前逐项重现本轮异常，修复后正常 64 kHz AAC 间隔在 15–17 ms 内且无零/负间隔 |
| RtspMuxer 本地复现 | 音频先到、视频先到、轨道加入顺序交换，均不产生 415 ms 类只改 NTP 的跳变；跨轨偏移守恒 |
| 四相机冷启动 | 当前编码及 G711A/G711U/AAC + H264/H265 支持组合，重复启动至少 3 次；保留完整第一至第三份 SR |
| 整条链 SR | camera→proxy、FFmpeg→relay、relay→NVR 各层单独验证；不能只数 relay 音频负跳 |
| 配置兼容 | 以实际 `modify_stamp=0` 为主，显式测试 1/2 及用户更改后的有效值，不用改默认值代替修复 |
| 时间边界 | RTP wrap、同 SSRC 重启、丢包、变长包、AAC 多 AU/分片、VOD seek、B 帧、编码参数变化 |
| 延迟与恢复 | 同内容、同窗口 P50/P95/P99；初始积压及短时阻塞恢复；超过 3 秒的积压必须验证 NtpStamp 行为并明确恢复策略 |
| 长时钟 | 至少 1 小时、正负 100 ppm、持续小校时与大校时；验证不把合法漂移永久冻结，不积累音画偏移 |
| 实际播放器 | RTSP/NVR 音画同步、重连、录像连续性；日志阶段耗时不能代替显示/听音验收 |

原版 FFmpeg SR 模式仍假定 nominal clock，输出起点不自动等于真实采样 UTC。当前短测没有证明任意频差、长时间停供、严重积压和任意 PTS 滤镜下都正确。泛化 PRFT/采样 UTC 穿过重采样、AAC/RKMPP 编码器及滤镜的传递会显著扩大修改范围，本轮不推荐引入；若上述必需验收失败，再依据失败证据调整设计，不能直接宣布通过。

本轮新增运行时代码行数为 0。拟议范围为两个命令生成文件及四个 ZLM 文件，另加相应回放/回归测试；不预估尚未实现的精确行数。已有工作区修改与无关 `www/http-flv/` 均保留。

## 运行环境收尾

最终核验生产 `MediaServer`、`compress`、`config.ini` 哈希均未变，有效配置变化键为空，`modify_stamp=0`。原有 13 路 RTSP 流在线；本轮候选测试进程为 0，临时实例配置和远端私有源地址/配置快照已删除。

协议参考：[RFC 3550 §6.4.1](https://www.rfc-editor.org/rfc/rfc3550#section-6.4.1) 要求 SR 的 NTP 与 RTP 表示同一时刻，SR 的 RTP 通常不等于邻近媒体包的时间戳。该约束用于解释配对问题，并不意味着只消除回退就满足所有同步要求。
